# Immich API notes (observed on the live v3.3.1 server)

Things that behaved differently from what the OpenAPI spec alone suggests, and how
ShutterStorm handles them.

| # | Observation | Consequence | Handling in ShutterStorm |
|---|-------------|-------------|--------------------------|
| 1 | `POST /api/search/smart` with a query text that was already searched answers in ~70 ms **even while the ML container is paused** (observed: 36/36 OK during a pause). *Inferred, not verified in Immich's source:* the server caches the CLIP text embedding per query string. | A probe that always searches `"tree"` never reaches ML and hides the M-01 hang. Our first `inject ml_pause` run showed J3 36/36 OK for this reason. | J3 sends a unique query per call (`tree <run> <n>`). The warmup also uses a unique query. |
| 2 | `POST /api/search/metadata` accepts `originalFileName` as an exact filter. | An upload whose HTTP response never arrived (timeout) can still be found afterwards. | `AssetTracker.reconcile()` finds these "ghost uploads" so cleanup deletes them and the integrity score counts them. |
| 3 | `machineLearning.availabilityChecks` is **already enabled** by default (`timeout 2000`, `interval 30000`) with a single ML URL. | The availability check alone does not prevent the M-01 hang: with only one URL there is nowhere to fail over to. | The Repair agent adds a second ML URL/instance instead of only toggling the check. |
| 4 | `docker update --cpus 0 <container>` is accepted by Docker 29.8 and resets `NanoCpus` to 0 (unlimited). | No container recreation needed to undo `ml_cpu_throttle`. | `_restore_cpus` still falls back to `docker compose up -d --force-recreate <service>` if a Docker version rejects it. |
| 6 | `GET /api/assets/{id}/original` occasionally answers **404 within ~30 ms of a 201 upload** (seen once during `ml_stop`, unrelated to ML). *Cause unverified;* one guess is the storage-template job moving the file from `upload/` to `library/`. | A real but minor race; it would otherwise be blamed on the injected fault. | J6 retries once after 0.5 s on 404 and notes "retried after transient 404" in the probe's `error_text`. |
| 7 | **Mistral (not Immich):** our free-tier key gets `429 rate_limited` on every chat call to `mistral-small-latest`, `mistral-medium-latest` and `magistral-small-latest`; the response header shows `x-ratelimit-limit-req-minute: 0`. `ministral-8b-latest` (188 req/min) and `ministral-3b-latest` work. `GET /v1/models` lists all of them regardless. | With the default model every agent silently falls back. | We use `MISTRAL_MODEL=ministral-8b-latest`. The model sometimes ignores the requested JSON shape; schema validation + one retry + fallback handle it. Check the header if you see constant 429s. |
| 8 | Verified in the captured server logs: after we delete a probe asset whose jobs are still running, the server logs `PostgresError: insert or update on table "asset_job_status" violates foreign key constraint "asset_job_status_assetId_fkey"` (job `AssetDetectFaces`). | Harmless, but these lines show up in later log tails. The Analyst once quoted them as a fault symptom and invented a wrong table name (`smart_search`): a hallucination. | The Analyst prompt says log tails may contain older, unrelated lines, and the grounding check (#9) rejects answers that cite numbers not in the evidence or mention other faults. |
| 5 | `DELETE /api/assets` with `{"ids": [...], "force": true}` deletes permanently (skips trash) and answers 204. | | Only IDs we uploaded **and** whose `originalFileName` starts with `shutterstorm-probe-` are deleted. |
| 9 | **Mistral:** `ministral-8b` sometimes invents details (a table name, Java libraries such as Hystrix for a Node.js server) or blames a different fault. | AI text can sound right and be wrong. | `agents.grounding_errors`: every number an LLM cites must appear in the evidence, and an analysis may only mention its own fault; otherwise one retry, then the deterministic fallback. Repair recommendations that no test verified are labelled "AI suggestion, not verified by a test" in the report. |
| 10 | `docker stop immich_redis`: uploads **hang** (J4 timed out) instead of failing fast; the server log shows `missing 'error' handler on this Redis client`. | Contradicts the "down fails fast" pattern for Redis. | *Hypothesis, not verified:* the Redis client queues commands while disconnected. Reported as a finding; the simulator now models this as a hang too. |
| 11 | Verified with `docker inspect immich_postgres`: Immich's Postgres image has a healthcheck **interval of 300 s** (`/usr/local/bin/healthcheck.sh`). After `db_pause`, Docker kept reporting `unhealthy` for ~5 minutes although the database answered queries again (J1/J2 OK, ping OK). | Docker health status lags reality by up to 5 minutes in both directions, so anything that trusts it (orchestrators, `depends_on: condition: service_healthy`) reacts late. In our final run a repair attempt was wrongly failed because our 180 s health wait was shorter than one interval. | `wait_healthy` now waits at least one healthcheck interval + 30 s. |
